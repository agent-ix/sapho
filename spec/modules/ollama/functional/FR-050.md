# FR-050: Count prompt size in tokens and report inputs that do not fit

## Description

The Ollama adapter SHALL keep every request inside the binding's context by a conservative token estimate made before sending, treating the server's reported `prompt_eval_count` as a lower bound on the prompt size, and returning `TooLarge` with its numbers for an input that does not fit.

## Inputs

- The UTF-8 bytes of `system`, `prompt` and the serialized `format` schema of one request.
- The binding's `num_ctx`, `num_predict` and bytes-per-token ratio (default 3.0).
- The response's `prompt_eval_count` and `eval_count`, when present.

## Outputs

- `usage.estimated_input_tokens` on every request; `usage.input_tokens` and `usage.output_tokens` when the server reported them.
- An `estimate_exceeded` flag when the reported count exceeds the estimate by more than the tolerance.
- `TooLarge` with `estimated_input_tokens`, `reported_input_tokens` (when a response arrived), `context_tokens` (`num_ctx`) and `reserved_output_tokens` (`num_predict`).

## Behavior

Context limits are counted in the model's tokens, not in bytes. Measured on Ollama 0.32.14 with `qwen3:30b`, English requirement text averages about 4.3 bytes per token, so the default ratio of 3.0 overestimates and leaves a margin. The pre-send estimate is the guard that matters: the same server, given a prompt longer than `num_ctx`, silently keeps only part of it (a prompt of several thousand tokens with `num_ctx` 2048 reported `prompt_eval_count` 1026) and answers from the shortened text, so a truncated prompt cannot be recognized after the call. The reported count is used only as a lower bound: on 0.32.14 it counts the whole prompt even when the server reuses a cached prefix, but a server that counts only newly evaluated tokens can report less, never more.

- When a request is about to be sent, the adapter SHALL compute `estimated_input_tokens` as the combined UTF-8 byte length of `system`, `prompt` and the serialized schema divided by the binding's bytes-per-token ratio, rounded up.
- If `estimated_input_tokens + num_predict` exceeds `num_ctx`, then the adapter SHALL return `TooLarge` without sending a request.
- If a response reports `prompt_eval_count + num_predict` above `num_ctx`, then the adapter SHALL return `TooLarge` with the retained raw exchange and usage, because even the lower bound of the prompt does not fit.
- When `prompt_eval_count` exceeds `estimated_input_tokens` by more than 15 percent of the estimate, the adapter SHALL set `estimate_exceeded` on the response's usage, which is evidence that the ratio is too high for this model and text; both numbers are always kept.
- If a response lacks `prompt_eval_count` or `eval_count`, then the adapter SHALL return the answer with that count absent from usage, `estimate_exceeded` unset and no post-call check; a missing count is never an error and never causes a retry.
- The adapter SHALL NOT shorten, compress or re-encode any part of a request to make it fit.

## Acceptance Criteria

| ID | Criteria | Verification |
|----|----------|--------------|
| FR-050-AC-1 | With `num_ctx` 1000, `num_predict` 200 and ratio 3.0, an input whose estimate is 801 tokens is refused with `TooLarge` carrying estimate 801, context 1000 and reserved output 200, and the loopback server records zero requests; an input estimated at 800 tokens is sent. | Test |
| FR-050-AC-2 | A sent request whose response reports `prompt_eval_count` 900 with `num_ctx` 1000 and `num_predict` 200 yields `TooLarge` with reported count 900, the raw exchange and usage retained, and the caller can continue with its next item. | Test |
| FR-050-AC-3 | A reported count 16 percent above the estimate sets `estimate_exceeded`; 15 percent above does not; a reported count below the estimate (as with a cached prefix) never sets it; all cases keep the estimate and the reported count. | Test |
| FR-050-AC-4 | A response missing `prompt_eval_count`, and one missing `eval_count`, each return the schema-valid answer with that usage count absent and no error; repeating the call gives the same result. | Test |
| FR-050-AC-5 | A non-ASCII input is estimated from its UTF-8 byte length, and the request body carries the input bytes unchanged. | Test |
