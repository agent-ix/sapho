# FR-050: Let the server count prompt tokens and report inputs that do not fit

## Description

The Ollama adapter SHALL return `TooLarge` with its numbers for every input whose prompt does not fit the binding's context, taking the server's own token count as the only authority and never shortening a prompt.

## Inputs

- The binding's `num_ctx` and `num_predict`.
- The server's context refusal, or the response's `prompt_eval_count` and `eval_count`, when present.

## Outputs

- `usage.input_tokens` and `usage.output_tokens` when the server reported them.
- `TooLarge` with `reported_input_tokens` (the server's count, when it gave one), `context_tokens` (`num_ctx`) and `reserved_output_tokens` (`num_predict`).

## Behavior

Context limits are counted in the model's tokens, and only the server's tokenizer knows the count. Measured on Ollama 0.32.14 with `qwen3:30b`, bytes per token vary by two orders of magnitude: digit lists 1.0, tables 1.3, identifiers 2.2, Rust code 3.5, Chinese text 4.1, English prose 5.3, and whitespace-heavy text 109. No byte ratio bounds the token count in either direction, so the adapter makes no estimate and refuses nothing before sending. With `truncate: false` the server itself answers a prompt longer than `num_ctx` with HTTP 400, error type `exceed_context_size_error` and the exact `n_prompt_tokens`, where it would otherwise keep only part of the prompt and answer from the shortened text. The refusal is quick (0.3 to 1.4 seconds for prompts of 176 KB to 1.8 MB measured), and the request byte ceiling of [FR-051](FR-051.md) bounds what is sent.

- If the server answers HTTP 400 with error type `exceed_context_size_error`, then the adapter SHALL return `TooLarge` with `reported_input_tokens` set to the server's `n_prompt_tokens`.
- If a response reports `prompt_eval_count + num_predict` above `num_ctx`, then the adapter SHALL return `TooLarge` with the retained raw exchange and usage, because the prompt left too little room for the answer; this takes precedence over `output_truncated`.
- If a response lacks `prompt_eval_count` or `eval_count`, then the adapter SHALL return the answer with that count absent from usage and no post-call check; a missing count is never an error and never causes a retry.
- The adapter SHALL NOT refuse a request for its size before the server has counted it, other than by the request byte ceiling.
- The adapter SHALL NOT shorten, compress or re-encode any part of a request to make it fit.

## Acceptance Criteria

| ID | Criteria | Verification |
|----|----------|--------------|
| FR-050-AC-1 | A scripted HTTP 400 whose body carries error type `exceed_context_size_error` and `n_prompt_tokens` 4112 yields `TooLarge` with reported count 4112, context and reserved output from the binding; a 400 of another type yields `BackendFailed`. | Test |
| FR-050-AC-2 | A whitespace-heavy prompt of 20,000 bytes with `num_ctx` 1000 reaches the loopback server (no size refusal before sending), and the server's answer decides the outcome. | Test |
| FR-050-AC-3 | A response reporting `prompt_eval_count` 900 with `num_ctx` 1000, `num_predict` 200 and `done_reason: length` yields `TooLarge` with reported count 900, not `output_truncated`, with raw exchange and usage retained, and the caller can continue with its next item. | Test |
| FR-050-AC-4 | A response missing `prompt_eval_count`, and one missing `eval_count`, each return the schema-valid answer with that usage count absent and no error; repeating the call gives the same result. | Test |
| FR-050-AC-5 | A non-ASCII input reaches the server with its bytes unchanged. | Test |
