# FR-037: Compare bounded development candidates

## Description

The Sapho tuning tools SHALL compare explicit candidate graphs using development cases only.

## Inputs

The explicit typed inputs, options and limits named in Behavior. External files and JSON/YAML are validated before evaluation.

## Outputs

The declared typed result, or a structured refusal. Execution failures retain available partial evidence; absence of a result is never interpreted as a passing evaluation.

## Behavior

tune takes a bounded ordered list of candidate graph paths, an identified dataset, the output/metric being compared and explicit replay or backend bindings. It evaluates development cases only and retains per-candidate graphs/identities, case IDs, metrics, failures and model request evidence. Candidates are authored explicitly; the CLI does not mutate a source graph or invent thresholds/questions. A candidate is rankable only when all selected development labels for the selected output are scored without failure; Boolean agreement is maximized and Probability Brier score minimized, with input order as the tie-break. No candidate/no development cases/no rankable candidate is an explicit error. Changed model requests in replay fail exactly rather than reusing approximate matches. Held-out cases are never selected for tuning.

## Acceptance Criteria

| ID | Criteria | Verification |
|----|----------|--------------|
| FR-037-AC-1 | Two threshold candidates evaluated on development cases produce the expected metrics, rank and deterministic tie-break. | Test (TC-037) |
| FR-037-AC-2 | Held-out cases cause zero backend calls in tune; replay-incompatible and incomplete candidates remain failures and cannot win. | Test (TC-037) |
| FR-037-AC-3 | Candidate-count ceilings, empty development sets and no rankable results are refused without overwriting graphs, labels or recordings. | Test (TC-037) |
