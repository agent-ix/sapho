# FR-055: Run local Ollama models from CLI bindings

## Description

The Sapho CLI SHALL accept the provider `ollama` in a bindings document and, for a required binding of that provider, build the existing Ollama backend, so that `record`, `run`, `measure` and `tune` can run a local model and replay the recording offline.

## Inputs

- A bindings document entry `provider: ollama` with `model` (required), optional `expected_model`, `distribution_policy` (as for the other providers), and optional `think` (default `false`), `num_ctx` (default 32768), `num_predict` (default 512) and `timeout_seconds` (default 600, the adapter default of [FR-051](../../ollama/functional/FR-051.md)). The generation members are those of [FR-049](../../ollama/functional/FR-049.md); the defaults are the CLI's own and are owned here, not by the adapter. The default `num_predict` of 512 suits typed questions, whose answers are a few tokens; a binding used to extract records needs a larger value.
- The environment variable `OLLAMA_BASE_URL`, an optional base URL of the Ollama server; the default is the loopback URL of the Ollama module.

## Outputs

A binding for the existing Ollama backend ([FR-054](../../ollama/functional/FR-054.md)) for each required name of provider `ollama`; recordings whose exchanges carry the reported model name and the weights digest ([FR-052](../../ollama/functional/FR-052.md)); typed refusals.

## Behavior

The Ollama backend already exists in the workspace, and the CLI could not use it: its providers were the hosted and service ones only. Adding the provider exposes the backend with the same credential-free, bounded and replayable behavior the other providers have, so a graph that was recorded against a hosted provider can be recorded against a local model by changing only the bindings document.

### Bindings and endpoint

- The bindings document SHALL accept `ollama` as a provider spelling and refuse an unknown provider.
- `deny_unknown_fields` SHALL still refuse an unknown member of any entry, including an `endpoint`, `url`, `api_key` or other credential-like member for every provider, since an endpoint is never read from a bindings document.
- The CLI SHALL read the Ollama server URL from `OLLAMA_BASE_URL` and otherwise use the default loopback URL, never from a bindings document, a graph or a recording.
- A URL the Ollama module refuses SHALL be refused before any request, with the module's typed error.
- `OLLAMA_BASE_URL` MAY name a host other than the local machine: the adapter accepts any `http` or `https` URL without userinfo ([FR-051](../../ollama/functional/FR-051.md)). That is the operator's choice, it means that prompts and state leave the machine, and a recording does not say which host answered, since it holds the model name and weights digest and never a URL or header; an operator who needs to show that a run stayed local keeps the environment with the run.

### Construction and replay

- The CLI SHALL construct the Ollama backend only for a binding that the invoked command requires and that calls a model live (`run`, `record`, and the live forms of `measure` and `tune`).
- Validation, inspection, replay and replay-backed `measure` and `tune` SHALL NOT construct the backend, read the environment variable or touch the network ([FR-045](FR-045.md)).
- The CLI SHALL pass `model`, `think`, `num_ctx`, `num_predict` and `timeout_seconds` unchanged to the backend's settings, so that the backend's own refusals (zero values, `num_predict` not below `num_ctx`, an empty model, `think: true` for questions) are the refusals the user sees.
- The model identity of a binding SHALL be the model name and the weights digest the server reports through the backend ([FR-052](../../ollama/functional/FR-052.md)), and the CLI SHALL NOT take the digest from the bindings document.
- A recording SHALL carry the model name and the weights digest on the exchanges it holds, and replays under explicit metadata exactly as [FR-035](FR-035.md) states, from the recorded name and policy, without a live provider.

### Timeouts

- The binding's `timeout_seconds` SHALL bound each single request to the server, and the run limit `--timeout-secs` ([NFR-005](../non-functional/NFR-005.md), default 60) SHALL bound the whole evaluation of a case; whichever deadline comes first ends the call with the typed deadline error of its layer, and neither is raised implicitly.
- A first request that loads a large model can take longer than 60 seconds, so an operator running a cold model SHALL raise `--timeout-secs` to at least the binding's `timeout_seconds` (the CLI guide says so); the CLI never retries a deadline.

### Credentials, tests and documentation

- The provider SHALL need no secret store, and a build without Ollama provider support SHALL refuse a required `ollama` binding with `Config` before any network access, as for the other providers.
- Default tests SHALL run offline against a loopback double of the server or against recordings.
- A live smoke test against a real server SHALL run only when an environment flag asks for it.
- The CLI help and the CLI guide SHALL list `ollama` among the providers, with its members, the environment variable and the timeout rule.

## Acceptance Criteria

| ID | Criteria | Verification |
|----|----------|--------------|
| FR-055-AC-1 | A bindings document with `judge: {provider: ollama, model: "qwen3:30b", distribution_policy: {kind: strict}}` loads with the defaults `think` false, `num_ctx` 32768, `num_predict` 512 and `timeout_seconds` 600; the same entry with an unknown member, with `endpoint`, with `api_key` and with an unknown provider `foo` is each refused naming the member or provider. | Test |
| FR-055-AC-2 | `sapho record` of a one-question graph with an `ollama` binding against a loopback double of the server writes a recording; `sapho measure --replay` of that recording over a labelled Dataset gives the same report offline, with the server stopped, the network disabled and `OLLAMA_BASE_URL` unset. | Test |
| FR-055-AC-3 | The recording holds, for each exchange, the model name and the weights digest the double reported through the model description, never a digest from the bindings document; a bindings entry cannot carry a digest member. | Test |
| FR-055-AC-4 | `validate`, `inspect`, `replay` and replay-backed `measure` and `tune` with an `ollama` binding construct no backend: the double records zero requests and the environment variable is not read. | Test |
| FR-055-AC-5 | A live `run` with `think: true` for a question is refused with the backend's `think_unsupported_for_questions`, and a live `record` with `num_ctx: 0` with the backend's `Config` refusal, each before any request reaches the double. | Test |
| FR-055-AC-6 | With `OLLAMA_BASE_URL` naming the double, the live run reaches it; with it unset the default loopback URL is used; the URL appears in no bindings document, recording or diagnostic. | Test |
| FR-055-AC-7 | Against a double that delays its answer by 2 seconds, a live `record` with `timeout_seconds` 1 fails with the adapter's deadline error; with `timeout_seconds` 600 and `--timeout-secs` 1 it fails with the run deadline error; with `timeout_seconds` 600 and `--timeout-secs` 10 it succeeds; no deadline is retried. | Test |
| FR-055-AC-8 | `sapho --help` and the CLI guide list the provider `ollama`, its `model`, `expected_model`, `distribution_policy`, `think`, `num_ctx`, `num_predict` and `timeout_seconds` members, `OLLAMA_BASE_URL` (stating that a non-local host is allowed) and the timeout rule; the default test run makes no request outside the loopback double and a live smoke test runs only with its environment flag set. | Test |
