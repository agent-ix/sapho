# FR-073: Keep named System One bindings distinct through recording and replay

## Description

When a graph calls multiple configured System One services, the CLI SHALL preserve each BackendId through live dispatch, recording and exact offline replay while retaining existing Jev and CLM binding behavior.

## Inputs

Compiled required BackendIds, credential-free binding metadata, per-binding host service configuration for live runs, and an optional exact Recording for replay. The generic provider uses the existing `ModelRequest` and shared System One request contract.

## Outputs

Per-binding live responses and typed recordings keyed by BackendId, or exact replay results with no host service configuration or credential access. Existing Jev/CLM outputs and errors remain compatible.

## Behavior

The CLI SHALL construct one backend instance per required generic binding from that binding's host entry.

It SHALL not use a process-wide endpoint for generic services.

The CLI SHALL send each request with its declared BackendId, requested model, expected-model constraint and DistributionPolicy through the existing System One translator and response validation.

The recording decorator SHALL retain each successful exchange's original BackendId and typed request/response without adding endpoint, credential key or secret value.

Replay SHALL distinguish recorded requests by BackendId and exact request content. It SHALL infer only the existing model/expected-model/distribution-policy identity per binding or compare explicit credential-free metadata, without inferring or requiring a provider, endpoint or credential.

The CLI SHALL refuse a replay miss or conflicting recorded identity without falling back to live transport, service configuration or credential lookup.

The CLI SHALL retain `provider: jev` SDK endpoint/credential behavior and `provider: clm` CLM_BASE_URL, CLM_API_KEY/OS-store precedence, default model and feature-gate behavior. New generic configuration SHALL not change those legacy bindings.

A custom Rust host SHALL remain able to register any ModelBackend directly through the public core port.

## Acceptance Criteria

| ID | Criteria | Verification |
|----|----------|--------------|
| FR-073-AC-1 | A graph asking `fast_a` and `fast_b` receives distinct captured responses from two loopback ports and the recording retains two corresponding BackendIds without URL, key or credential bytes. | Test |
| FR-073-AC-2 | Replaying that recording reproduces both outputs with the two BackendIds while host service file and secret store are unavailable; changing one binding or request yields ReplayMiss rather than a live call. | Test |
| FR-073-AC-3 | Adding `fast_c` through only binding metadata, host service configuration and graph edits dispatches to a third fake contract service through the same adapter implementation. | Test |
| FR-073-AC-4 | Existing Jev and CLM binding fixtures retain their endpoint/credential precedence, model default or required-model rule, feature refusal, recording and replay behavior. | Test |
| FR-073-AC-5 | A custom core ModelBackend still works without a stock provider, and Dataset JSON/serde/validate plus the EARS production boundary remain unchanged. | Test |

## Dependencies

[FR-035](FR-035.md) owns exact CLI recording/replay, [FR-045](FR-045.md) owns existing Jev and CLM behavior, and [FR-072](FR-072.md) owns generic service host configuration. System One is a wire contract, not a model-quality claim or installation mechanism.
