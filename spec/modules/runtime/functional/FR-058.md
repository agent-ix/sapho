# FR-058: Execute shadow asks without changing decisions

## Description

The executor SHALL run shadow work after a successful decision evaluation.

When shadow work fails, the executor SHALL return the completed decision outputs and decision exit status.

## Inputs

A compiled graph with its separate shadow-work plan, case inputs, backend registry, recording or replay backend, and one shared RunLimits value.

## Outputs

The existing decision result plus ordered shadow observations in the trace and run report. Each shadow observation carries its shadow node ID, mapped decision output, case ID when measured, projected value when available, request/response evidence when available, and a completed, failed or skipped status with a typed reason.

## Behavior

The executor SHALL finish the decision graph before scheduling any shadow-only producer or shadow ask.

When the decision fails, the executor SHALL schedule no shadow asks.

Shadow asks SHALL use the same input item and the shadow's own question and backend bindings.

The executor SHALL reuse completed decision-stage values for shared ask-free producers and execute shadow-only producer closures in dependency order after decision success. Their node instances, expanded items, data bytes and elapsed time are charged to the same RunLimits only in the shadow phase. A shadow-only producer error or exhausted limit marks its dependent shadow observation failed or skipped with the typed reason and retained partial shadow trace; it does not change completed decision outputs or exit status. Independent shadows whose inputs remain available can continue within remaining limits.

A shadow result SHALL never enter decision dataflow.

When a shadow backend returns an error, times out, gives a malformed response or misses in replay, the executor SHALL preserve the decision output bytes and decision exit status.

The executor SHALL retain the shadow failure and available raw exchange in the trace.

Successful shadow exchanges SHALL use the existing recording decorator and exact replay key.

Failed calls SHALL remain trace evidence rather than successful exchanges.

Each scheduled shadow request SHALL consume one global model-request credit.

Each scheduled shadow request SHALL remain subject to the existing concurrency, data-byte and elapsed-time limits.

Decision work has priority: when no credit or time remains after the decision, the executor SHALL mark the shadow `skipped` with the relevant limit reason without making a backend call.

There is no separate shadow budget and no retry.

Existing graphs without shadow work retain their run result and trace shape.

## Acceptance Criteria

| ID | Criteria | Verification |
|----|----------|--------------|
| FR-058-AC-1 | With a fixed champion recording, adding a successful shadow ask leaves the serialized decision outputs byte-identical and records the challenger exchange. | Test |
| FR-058-AC-2 | A shadow backend error, timeout, malformed answer or replay miss leaves the champion decision and exit code unchanged; the trace identifies the shadow node, failure code and available raw evidence. | Test |
| FR-058-AC-3 | With a model-call ceiling equal to the champion's call count, no shadow backend call occurs and its observation is `skipped` for LimitExceeded; one extra credit permits exactly one shadow call. | Test |
| FR-058-AC-4 | A shadow deadline or data-byte limit does not erase a completed decision; the shadow observation names the limit and all calls remain bounded by RunLimits. | Test |
| FR-058-AC-5 | A replayed successful shadow exchange gives the same projected observation without live transport; a missing exchange gives a shadow ReplayMiss and preserves the decision. | Test |
| FR-058-AC-6 | A shadow-only native producer failure or exhausted node/data/time limit occurs after the champion decision, causes no dependent shadow backend call, and retains the decision bytes/exit plus the producer's typed shadow trace; a shared producer executes once in the decision phase and is reused. | Test |
